# Дедубликация и идемпотентная обработка

Система не обещает exactly-once delivery на всём пути. Kafka и publisher обеспечивают at-least-once доставку, а уникальные ключи и транзакции PostgreSQL не позволяют применить событие повторно.

## Приём в API

1. API нормализует пробелы в идентификаторах, приводит валюту к заглавным буквам и приводит `occurred_at` к UTC.
2. Проверяет обязательные поля, размер идентификаторов, тип события, положительный integer `amount_minor`, трёхбуквенную валюту и `schema_version = 1`.
3. Считает SHA-256 от сериализованной нормализованной структуры события. В hash входят все поля JSON-события.
4. В транзакции PostgreSQL вставляет событие с уникальным ключом `UNIQUE(source, event_id)`, а при новом событии — и строку Outbox.
5. При существующем ключе сравнивает hash. Равный hash означает полный дубль: API возвращает `200`, не создаёт Outbox повторно. Разный hash означает конфликт: тело и hash сохраняются в `ingestion_conflicts`, API возвращает `409`.

Конфликт сохраняется отдельно и не заменяет первоначально принятое событие. Так можно разбирать ошибки источника, не переписывая уже поставленные на обработку финансовые данные.

## Передача через Outbox

Событие и Outbox фиксируются одной транзакцией. Publisher не удаляет строки: после подтверждённой записи Kafka он ставит `published_at`, а при временной ошибке увеличивает `attempts` и сохраняет `last_error`. Если publisher падает после Kafka ack, но раньше `published_at`, та же запись будет повторно отправлена. Это ожидаемое окно at-least-once доставки.

## Обработка каждого consumer

`processed_messages` имеет первичный ключ `PRIMARY KEY (consumer_name, source, event_id)`. Поэтому payment и analytics consumer независимо обрабатывают событие по одному разу каждый.

В транзакции payment consumer:

- регистрирует ключ и hash сообщения;
- проверяет, что сохранённое приёмное событие имеет тот же hash;
- создаёт или изменяет платеж;
- добавляет переход в `payment_history`;
- фиксирует транзакцию и лишь затем подтверждает Kafka offset.

В аналитическом consumer ключ дедупликации и upsert дневного агрегата находятся в той же транзакции. Если процесс завершился до commit, откатывается и ключ, и изменение агрегата. Если commit прошёл, но Kafka offset не подтвердился, повторная доставка найдёт ключ и не применит агрегат повторно.

Повтор одного event ID с иным содержимым на любом этапе обработки считается конфликтом и не применяется. Нарушенный переход статуса откатывается вместе с отметкой `processed_messages`, повторяется ограниченное число раз и затем попадает в DLQ. Offset подтверждается только после успешной отправки DLQ.

## Почему ключ — не `payment_id`

Один платёж законно порождает несколько событий: создание, успешное завершение или отказ. Если дедуплицировать только по `payment_id`, система отбросит последующие состояния как дубликаты. Идентичность доставки задаётся `(consumer_name, source, event_id)`, а `payment_id` используется для агрегации состояния одного платежа и Kafka partition key.

События `payment.created`, `payment.succeeded` и `payment.failed` проверяются по конечному автомату статусов. Один и тот же статус повторно не добавляет строку истории; смена одного terminal-статуса на другой запрещена. Баланс клиента не ведётся, поэтому повторная обработка не может повторно списать или зачислить сумму.
